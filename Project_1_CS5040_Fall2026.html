Overview:

In most programming languages, integer values are of a fixed size, e.g., 32 bits in C++, 64 bits in Java. 32 bits will allow integers of approximately 10 decimal digits. For most purposes this is sufficient, but when it is not, infinite precision integer arithmetic can be implemented in software. For this project you will complete a "BigNumArithmetic" or infinite precision arithmetic package for non-negative integers.

The program will be invoked from the command-line as:

%> java BigNumArithmetic <input-file>

where:

  • BigNumArithmetic is the name of the program. The file where you have your main() method must be called BigNumArithmetic.java
  • input-file is the name of the text input file to be read.
Your program will read, from the input-file, a series of expressions with one expression per line. The program should terminate after reading the end of the file.

All expressions are in Reverse Polish Notation (RPN) (postfix expression). In RPN, the operands come before the operator. For example, you normally see multiplication written as (a * b). In RPN, this expression would appear as (a b *). For expressions with more than one operator, each time an operator is encountered, it operates on the two immediately preceding sub-expressions. Thus (a + b * c) is (a b c * +) and ((a + b) * c) is (a b + c *). In RPN there is no operator precedence; operators are evaluated left to right.

Input operands consist of a string of digits and may be of any length. You should trim off any excess zeros at the beginning of an operand. Expressions may also be of any length. Spaces may appear within the expression arbitrarily, with the rule that a space terminates an operand and a line break terminates an expression. The operations to be supported are addition (+), multiplication (*), and exponentiation (^). Your program must not break if the number of operators and operands do not match correctly. When an error is detected, processing stops on the current expression and your program proceeds to the next expression.

For each expression, echo the input as it is read to stdout, followed by the result of the operation, or a blank space for an error, as appropriate. Given 2 8 + 2 ^ you print:

2 8 + 2 ^ = 100

If an error is detected, e.g. 2 8 + 2, print:

2 8 + 2 =

Design Considerations

RPN can be implemented using a stack. As the expression is read in, operands are placed on the stack. Whenever an operator is read, the required operands are removed from the stack, the operation is performed, and the result is placed back onto the stack. You may assume the stack never holds more than 100 operands.

Integers are represented by a linked list of digits, one digit per list node. You must maintain a linked list of nodes as discussed in class and allocate new nodes with the new operator as needed. You will likely find that operations are easier to perform if the list is stored low order to high order.

Example: the integer 436 may be represented as 6 -> 3 -> 4. Results must be printed in the correct order, so convert between representations as appropriate.

Addition is performed by starting at the low order digits and adding each pair as you move toward the high order digits, carrying whenever a digit sum reaches ten.

Multiplication is performed as you learned in elementary school. The low order digit of the second operand is multiplied against the entire first operand; the next digit is multiplied against the first operand with a shift; each partial result is added to the running total.

Exponentiation must use exponentiation by squaring, which exploits the observation that for a positive integer n:

xn = x · (x2)(n-1)/2, if n is odd
xn = (x2)n/2, if n is even

Repeated multiplication is not acceptable, and Part C will make the difference visible in your own measurements. Addition, multiplication, and exponentiation may be implemented iteratively or recursively, as you prefer.

Part A: Defect Repair (15 pts)

Download bignum-defective.zip from Canvas. It contains a complete BigNumArithmetic that compiles, runs, and produces correct output on the sample input. It also contains six seeded defects. Some are correctness defects that appear only on particular inputs; at least one is a performance defect that produces correct answers at asymptotically worse cost than the specification requires.

Deliverable: DEFECTS.md, using the template provided, with one entry per defect containing

  1. the symptom, described as an observable behavior;
  2. a minimal failing input, meaning that no shorter or simpler input in the same family exposes the defect;
  3. the root cause, identified by file, method, and line, and explained in terms of the data structure invariant that is violated;
  4. your fix, and why you chose it over alternatives;
  5. a regression test that fails before the fix and passes after it.

Scoring: 2 points per defect for a correct root cause plus a locking test, 1 point for a correct fix with no correct root cause, 0 for a reported defect that is not actually in the code. The remaining 3 points are for the quality of your minimal inputs across the whole report.

Here is the category list. There is exactly one defect in each, and no defects outside them:

  1. exponentiation control flow
  2. linked list equality
  3. the size invariant after a list is truncated
  4. access to the top of the stack
  5. input tokenization
  6. asymptotic cost of a list operation used inside a loop

Three of the six produce no visible symptom when you run BigNumArithmetic on any input at all. You will not find those by running the program. Read the code, write unit tests against LinkedList, LinkedNode, and Stack directly, and check the class invariants documented at the top of LinkedList.java against what the methods actually do. One of the six produces correct output on every input and is detectable only by measurement.

Part B: Adversarial Test Suite (15 pts)

Submit BigNumTest.java, a JUnit suite that tests the public API of your package. Your suite is run against twelve hidden mutant implementations plus one correct reference implementation.

Your score is computed as follows.

  • +1.5 points for each mutant your suite detects, meaning at least one of your tests fails on that mutant. Capped at 15.
  • −3 points if any of your tests fails on the correct reference implementation. A test suite that rejects correct code is worse than no test suite.
  • 0 points for the part if your suite does not compile against the published API, or if any single test runs longer than 10 seconds.

The mutants are drawn from these families, one or two per family: carry propagation and carry-out when a result grows in length, zero and identity operands, single-digit versus multi-digit boundary cases, operand length asymmetry in multiplication, exponent parity in exponentiation by squaring, high-order zero normalization, malformed expression recovery, and aliasing between operands (computing x x * where both arguments are the same object).

Assertions on printed output alone will detect few mutants. The strongest suites test the data structure invariants directly.

Part C : Empirical Cost Study (15 pts)

This is the largest single component of the project and it is where the algorithm analysis content of the course is assessed.

Instrumentation. Your implementation must maintain counters, exposed through the starter code OpCounter interface, for

  • single-digit additions,
  • single-digit multiplications,
  • node allocations,
  • node traversals (pointer dereferences moving through a list).
The counters must be incremented in the arithmetic code itself, not estimated afterward. The grading harness re-runs your program on inputs you have not seen and compares the counter values your code emits against the numbers in your report. Reported numbers your code cannot reproduce score zero for the affected section.

Analysis. In ANALYSIS.pdf, no more than four pages:

  1. Measure. Run the provided generator to produce operands of 25, 100, 400, 1600, and 3000 digits, and exponents 21 through 212. Record counter values and wall-clock time, five trials each. Submit raw data as measurements.csv. Do not exceed 3000 digits until you have dealt with item 6 below.

Design Criteria (10 pts)

Included in the 100 points above. The following will negatively affect this component:

  • Inefficient code in the LinkedList structure.
  • Non-generic LinkedList and Node classes.
  • Significant redundant code that could have been generalized (for example, near copy-pasted blocks).
  • Inappropriate object-oriented technique: unnecessarily complex or constrained methods and classes, 80% or more of the code in a single class, or very large methods.
  • Input parsing, expression processing, and the linked list not decoupled into separate classes and files.
  • Instrumentation counters woven into the arithmetic so intrusively that the arithmetic becomes unreadable, or maintained so loosely that they are not exact.
  • Any forbidden library import.
